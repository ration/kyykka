# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

This is an early-stage Godot 4 project, now 3D. The game boots into a main menu that lets you pick a season (Summer or Winter — see Game modes below); the court then runs a full hot-seat match: mouse-aim/throw a karttu, turns alternate between two teams, halves reset the kyykkä and the match ends with a winner. A HUD shows running score/turn/karttu/kyykkä state (plus the active season), Esc opens a pause menu, and a results screen replaces the console-only end-of-match. No AI or real multiplayer yet — Phases 6-7. `scripts/rules/` remains the visual-independent source of truth for scoring and turn order.

The full game rules — field/square layout, kyykkä and karttu equipment, turn structure, and the plus/minus point scoring system — are documented in `README.md`. Read it before implementing any game logic: correctly modeling those rules (two opposing squares, alternating throws, pieces knocked out vs. left standing, two-half matches with sides swapped) is the core of this project.

`ROADMAP.md` tracks the phased task breakdown for the full game (rules engine, equipment, throwing physics, UI, AI, multiplayer, polish, release). Check it for current progress and update its checkboxes as phases complete.

## Engine and language

- Godot **4.7**, GDScript (no C# / .NET module involved), **3D** (`Node3D`/`Camera3D`/etc., not the 2D API).
- Rendering method is set to `gl_compatibility` in `project.godot` for broad hardware compatibility rather than `forward_plus`. Change this deliberately (and check it still runs) if a feature requires the Forward+ renderer.

## Game modes

`scripts/game_mode.gd` is an **autoload singleton** (registered as `GameMode` in `project.godot`'s `[autoload]` section) holding the season chosen from the main menu. Autoload rather than a scene-arg channel because `change_scene_to_file()` doesn't take arguments, and duplicating court/karttu scenes per mode would be worse. `GameMode.Mode` is `SUMMER` / `WINTER`; the singleton exposes helpers the court and karttu read from during their own `_ready()`:
- `karttu_friction()` / `karttu_landed_linear_damp()` / `karttu_landed_angular_damp()` — winter drops karttu friction 5x (0.1 → 0.02) and roughly halves landed damping so the karttu keeps sliding across the pesä after landing (real winter kyykkä on ice). Only the karttu is affected — kyykkä pieces still use the sturdy damping they need to stay upright and settle without rocking on `BoxShape3D` corners (see the corner-balance note under Throwing).
- `ground_low_color()` / `ground_high_color()` — the two ends of the ground's procedural noise gradient (sandy tones in summer, snow in winter — see `court.gd._build_ground_texture()`).

`scripts/ui/main_menu.gd` has two Start buttons (Start Summer Match / Start Winter Match) rather than a mode selector + Start, so a mode choice is one click. Each sets `GameMode.current` before `change_scene_to_file("res://scenes/court.tscn")`. The HUD reads `GameMode.mode_name()` once in `_build_ui()` and shows it in the top-left panel so the active season is visible during play.

## Court and equipment

`scripts/court.gd` (attached to the `Court` root of `scenes/court.tscn`) procedurally builds the ground plane, ground collision, ground texture (a small FastNoiseLite→ImageTexture whose two-colour gradient comes from `GameMode` — see Game modes above), and court lines at runtime rather than storing them as static scene geometry, so the dimensions live in one place (the script's `@export` fields) instead of being baked into hand-placed meshes. Current layout, per README.md: a 5×20 m court with a 5×5 m pesä square at each end (so only the two pesä "front lines" need drawing in addition to the outer boundary — the pesä's other three edges coincide with the court boundary). Throwing lines are not drawn yet since their exact placement wasn't pinned down from the rule sources. When adding throwing lines, extend this script rather than hand-authoring geometry in the `.tscn` file, to keep dimensions consistent and adjustable.

`scripts/court.gd` also gives the ground a `StaticBody3D`/`CollisionShape3D` (a flat box, `ground_margin` wider than the drawn court on each side) so `RigidBody3D` props have something to land on. It no longer builds any equipment or game-flow itself — it hands `MatchController` (see Match flow below) the dimensions/scenes/camera it needs and adds it as a child.

Equipment:
- `scenes/kyykka.tscn` — one kyykkä: `RigidBody3D` with a `CylinderMesh` for the visual (10 cm tall, ~7 cm diameter, per README.md) but a **`BoxShape3D`** (`0.09 × 0.1 × 0.09`, deliberately larger than the ~7 cm visual diameter — see the tunneling note under Throwing for why) for the *collision* shape (also see the stacking-stability note under Throwing for why it's a box at all), its own `PhysicsMaterial` (`friction = 0.9`), and `linear_damp = 0.5`/`angular_damp = 1.0` — see the struck-piece-never-settles note under Throwing for how these were tuned. `scripts/kyykka.gd` (`extends SettlingBody`) gets its "force-settle if stuck spinning in place" watchdog from the shared base class — see the corner-balance note under Throwing.
- `scenes/karttu.tscn` — one karttu (throwing bat): same visual/collision-shape pattern, 85 cm long, `mass = 2.0` (README: no weight restriction), lying on its side, its own low-friction `PhysicsMaterial` (0.1) so it slides through a target rather than stopping dead on landing, and **`continuous_cd = true`**: at throw speed it moves further per physics step than a kyykkä's diameter, so without CCD it can tunnel straight through a piece with zero collision response (diagnosed directly — see Throwing below — `continuous_cd` alone still missed most direct hits on kyykkä, so `scripts/karttu.gd` also sweeps its own shape ahead each step; see the tunneling note under Throwing). `linear_damp`/`angular_damp` aren't set on the scene at all — `scripts/karttu.gd` (`class_name Karttu`, `extends SettlingBody`) sets them dynamically depending on flight phase (see the flight-vs-landed-damping note under Throwing) and owns the in-flight spin lock via `_integrate_forces` — see the spin-lock/CCD note under Throwing for why it isn't just a `ThrowController` implementation detail.
- `scripts/pesa_view.gd` (`class_name PesaView`) — spawns `piece_count / 2` positions evenly spaced along local X, each holding a pair of kyykkä stacked one on top of the other (per README.md: 10 pairs stacked two high, not side by side), at a small inward offset from the front line (`spawn_inward_offset`, see Throwing below — not exactly on the line). `piece_count` defaults to `KyykkaMatch.DEFAULT_KYYKKA_PAIRS * 2` (see Rules engine below) so the visual count stays wired to the rules engine's constant instead of being a second hardcoded number. `to_pesa_local()` converts a world position into (x, depth-from-front-line) for `PieceClassifier`. `PesaView` only sets up the *initial* layout for a half — it doesn't remove pieces from the scene as they're scored out; `MatchController` replaces the whole `PesaView` (fresh kyykkä) between halves instead of trying to mutate one in place.

## Match flow (Phase 4 — see ROADMAP.md)

`scripts/match_controller.gd` (`class_name MatchController`) owns everything that changes over a match — court.gd only builds the static ground/lines/collision. It owns a `KyykkaMatch`, the current `Half`, both `PesaView`s + their `PesaScorer`s, and the single (hot-seat) `ThrowController`:
- `_start_half()` calls `kyykka_match.start_half()`, frees any existing `PesaView`s and builds fresh ones (so kyykkä counts reset every half), and builds matching `PesaScorer`s. Team A defends the near pesä and attacks the far one; team B the reverse.
- On `ThrowController.throw_settled`: scores the just-attacked side's `PesaScorer` into the current `Attack`, prints status, then advances the turn via `Half.next_attack()` (see Rules engine below) — or, if the half just finished, starts the next half or, if the match is finished, prints the final result and sets `thrower.enabled = false`.
- Reconfigures the single `ThrowController` for whichever side's turn it is via `configure(position, forward, watch_root)` rather than using two separate throwers — this **is** the hot-seat: same controls, repositioned. "Camera follows current thrower" (a ROADMAP Phase 4 bullet) falls out for free from this, since the camera is already derived from the thrower's transform.
- Emits `half_started(half_number)` / `turn_changed` / `attack_scored` / `match_finished` for the UI to subscribe to (see UI below), rather than reaching into UI nodes itself — the console `print`s are kept for headless debugging alongside the signals.
- Verified end-to-end with a throwaway headless script driving forced throws through a full 2-half match: turns alternate correctly, halves reset kyykkä counts, the match finishes and disables the thrower.

## UI (Phase 5 — see ROADMAP.md)

The game boots into `scenes/main_menu.tscn` (the project's `run/main_scene`), not straight into the court. Court still runs the match; a HUD, pause menu, and results screen overlay it. All UI is built in code in `_ready()` rather than as `.tscn` files (except `main_menu.tscn`, which needs to exist as a scene to be the boot target) — matches how `court.gd` and `throw_controller.gd`'s swing gauge build their geometry, so dimensions live in one place instead of being baked into hand-edited scene files.

- `scripts/ui/main_menu.gd` (attached to `scenes/main_menu.tscn`) — Start Match / Quit. Start calls `change_scene_to_file("res://scenes/court.tscn")`. `_ready()` restores mouse-visible and `paused = false` in case we came back here from a paused/captured match.
- `scripts/ui/hud.gd` (`class_name HUD`) — running score, current half, whose turn, karttu remaining, kyykkä in-square/on-line/removed for the target pesä. Instantiated by `court.gd`, handed a `MatchController` reference, and subscribes to that controller's `half_started`/`turn_changed`/`attack_scored`/`match_finished` signals. Holds no game state — every notification just triggers a full `_refresh()` that re-reads from the `MatchController`.
- `scripts/ui/pause_menu.gd` (`class_name PauseMenu`) — Esc-toggled overlay: Resume / Main Menu / Quit. Runs with `process_mode = PROCESS_MODE_ALWAYS` so it can un-pause itself while the tree is paused; toggles `Input.mouse_mode` between `CAPTURED` and `VISIBLE` on open/close so its buttons are actually clickable (the `ThrowController` captures the mouse for aim). `court.gd` sets `enabled = false` on `match_finished` so the results screen (below) owns exits from there.
- `scripts/ui/results_screen.gd` (`class_name ResultsScreen`) — hidden until `MatchController.match_finished`; on that signal, shows final per-team totals plus the winner (or "Tie") and Rematch / Main Menu / Quit buttons. Rematch reloads `court.tscn`; Main Menu goes back to `main_menu.tscn`.

`court.gd` wires all three overlays: it constructs the `MatchController`, then adds a `PauseMenu`, `HUD`, and `ResultsScreen` as siblings, handing the last two a reference to the controller and connecting `match_finished` to disable the pause menu.

**HUD scoring can't just call `KyykkaMatch.total_score()` mid-match (found and fixed once, worth knowing about):** `total_score()` sums each half via `Half.score_for()` → `Attack.score()`, and `Attack.score()` asserts the attack is finished — a proper final score isn't well-defined until then (penalties for kyykkä still standing and the unused-karttu bonus both depend on end-state). Calling it from the HUD's `_refresh()` on `attack_scored` crashed on the very first throw. Fixed by computing the display total in the HUD itself: finished attacks contribute `score()`, in-progress ones contribute their positive `pesa.removed` tally, so the scoreboard ticks up live without needing rules-engine changes.

## Throwing

`ThrowController` (`scripts/throwing/throw_controller.gd`) is pure input/physics — it doesn't know about the rules engine or whose turn it is. `MatchController` calls `configure(position, forward_direction, watch_root)` once right after adding it to the tree (for the first turn) and again on every turn change; `enabled = false` stops it accepting input once the match is over.
- Mouse-captured aiming: horizontal (yaw, clamped to `aim_cone_degrees` either side of whatever `forward_direction` the current turn set) and vertical (`_elevation_degrees`, clamped to `[min_elevation_degrees, max_elevation_degrees]`, reset each turn to `launch_elevation_degrees`, which points the camera at the target pesä's kyykkä row). **The look direction is not the throw direction** — aiming is "point at where it should arrive": `_aim_distance()` casts the camera's look ray onto the plane at `aim_target_height` (mid-height of a stacked pair), and `_throw()` solves the launch angle with `Ballistics.launch_elevation()` so the fixed-speed karttu arcs down through that height at that distance; looking at/above the horizon aims at `max_throw_distance`. A small centre crosshair (the mouse is captured, so nothing else shows the aim point) marks it. See the aim-model note below for why. `_look_direction()` is the 3D camera-look direction; `_aim_direction()` stays horizontal-only (used for the camera's stand-off position and as the throw's heading). Scroll wheel zooms by narrowing/widening `camera.fov` (`_fov_degrees`, clamped to `[min_fov_degrees, max_fov_degrees]`, reset to `default_fov_degrees` each turn) — a lens zoom, not a dolly, since the target pesä is 10-15 m away and moving the camera a meter or two wouldn't meaningfully change how close it looks. Throw *speed* is currently **fixed** (`throw_speed`) — variable power is a later feature; distance comes from the aim point. The skill mechanic is swing timing: holding the button sweeps a 0–180° gauge (a bare-bones `CanvasLayer` bar built in code — a placeholder; Phase 5 owns the real HUD) over `swing_seconds`; releasing at the middle (90°) spins the karttu exactly half a rotation by the time it lands — enough to bring it back to lying parallel to the stack it started broadside to (a "flush" hit) — releasing early/late under/over-rotates it, and running the gauge past 180° without releasing **cancels** the swing (shows a "MISSED SWING" flash, requires releasing and pressing again). Launches the (single, reused) karttu instance, then polls `RigidBody3D.sleeping` on it and the current target pesä's pieces (with a timeout) before emitting `throw_settled`. Repositions/reorients the *existing* `court.tscn` `Camera3D` each frame rather than creating a new one.
- `scripts/throwing/ballistics.gd` (`class_name Ballistics`) — pure drag-free projectile math (GUT-testable): `launch_elevation()` (lowest angle that reaches a given distance/height at a given speed, 45° fallback when out of range) and `flight_time()`. Exact only because the karttu flies with genuinely zero damping — see the damping-mode note under Throwing.
- `scripts/throwing/spin_calculator.gd` (`class_name SpinCalculator`) — pure math (GUT-testable): `spin_rate()` mapping gauge angle to angular speed (linear, 90°→exactly `PI` radians — half a rotation — over the flight time from `Ballistics.flight_time()`).
- `scripts/rules/piece_classifier.gd` (`class_name PieceClassifier`) — pure geometry (no Node dependency, GUT-testable): classifies a (x, depth) position against a pesä rectangle into `IN_SQUARE`/`ON_LINE`/`REMOVED` by distance to the nearest edge.
- `scripts/throwing/pesa_scorer.gd` (`class_name PesaScorer`) — bridges `PesaView`'s live positions to `PieceClassifier`, remembers each piece's last zone, and turns the transitions since the last call into a `ThrowResult` for `Attack.throw()`.

**Spin axis went through two wrong guesses before landing on the right one — worth knowing about if it needs revisiting:** the karttu spins about `Vector3.UP` (vertical) — a level, flat spin like a twirled baton or thrown frisbee, not a tumble. The karttu's length starts broadside (perpendicular to travel, so it can sweep across a row of kyykkä); yawing it 180° returns it to that same broadside alignment (symmetric end-to-end), while 90°/270° points it lengthwise down the throw direction instead — narrow, hits far fewer kyykkä. That's what "release at 90° to land flush" actually means physically. Earlier attempts got this wrong twice: first `dir.cross(Vector3.UP)`, which for a straight throw coincides with the karttu's own length axis (a no-op rolling-pin roll); then the horizontal aim direction itself, which tumbles the karttu end-over-end through vertical (pitching it up onto its end) instead of keeping it level — "spinning on the same plane as the ground" specifically meant the rotation *plane* should be horizontal, i.e. the axis is vertical, the opposite of what a horizontal-axis tumble does.

**Rotation is driven kinematically while airborne, not left to the physics solver — but doing this from outside the physics step silently broke CCD (found and fixed twice, worth knowing about):** setting `angular_velocity` once (or even re-asserting it every physics frame) still let the karttu's spin visibly wobble off-axis — measured directly: `angular_velocity`'s off-axis components reached double digits (rad/s) within a single physics step even with a per-frame reset, i.e. real solver-computed torque/precession, not float drift. The first fix overrode `global_transform.basis` every `Node._physics_process` tick from `ThrowController` with an exact analytic rotation, which did keep the geometry level — but `_physics_process` runs *after* that frame's physics step (CCD sweep included) has already completed, so externally rewriting the transform every frame was desyncing the physics server's own per-step motion tracking. This silently defeated `continuous_cd` on some frames even though CCD tested fine in isolation (that test bypassed the spin lock entirely) — surfacing later as reports of "sometimes hitting perfectly it just passes through." Verified directly: 10/10 close-range throws through the *real* `_throw()` path registered a hit once fixed, versus needing to bypass the spin lock to get reliable hits before.

The fix: the spin lock now lives on the karttu itself (`scripts/karttu.gd`, `class_name Karttu`) via `_integrate_forces(state)` — called by the physics engine *as part of* its own step, before finalization, so setting `state.transform`/`state.angular_velocity` here is consistent with whatever CCD sweep the engine computes for that step. `ThrowController.start_spin_lock(axis, rate)` on the `Karttu` at launch, `stop_spin_lock()` on reset; the lock itself still releases on first genuine contact, still ignoring `get_contact_count()` for a short grace period after launch since it can briefly still report the pre-launch resting-on-ground contact right after unfreezing. The resulting *feel* (does a flush hit visibly sweep more kyykkä than a bad-angle one) still hasn't been checked visually — get a screen-share or description before trusting another guess on this.

**Physics jitter caveat (found and fixed once, worth knowing about):** kyykkä standing upright on a flat plane are prone to slow RigidBody3D solver jitter even while nominally "at rest" — an early version placed pieces only 1.5 cm past `PieceClassifier`'s margin, and several seconds of *undisturbed* simulation was enough to drift them across it, scoring phantom hits. `PesaView.spawn_inward_offset` (0.15 m) and the kyykkä's damping are the fix; keep a healthy margin if either dimension changes.

**Stacked-pair stability needed a collision-shape swap, not just damping (found and fixed once, worth knowing about):** each pesä position holds two kyykkä stacked one on top of the other (see Court and equipment above). Two `CylinderShape3D`s in flat-face contact turned out to be a genuinely unstable resting configuration regardless of damping or spawn gap — diagnosed directly: left alone, the top piece of a stack drifted sideways and slid off within a few seconds, neither piece ever reaching sleep. Two other fixes were tried and abandoned before this one: freezing pieces until hit (a frozen `RigidBody3D` turned out not to reliably register collisions from a fast, `continuous_cd`-enabled body at all — diagnosed directly, a karttu at throw speed passed straight through a frozen kyykkä with zero response), and forcing `sleeping = true` at spawn (got overridden within one physics frame even for a single non-stacked piece). What actually worked: swapping the *collision* shape (not the visual mesh, which stays a `CylinderMesh`) to a `BoxShape3D` — box-on-box contact gives the solver a stable multi-point manifold that a round flat-face contact doesn't, so the stack now settles and sleeps naturally within about a second. The box started out *inscribed* in the visual cylinder (side = `radius * sqrt(2)` ≈ `0.0495`) but was later deliberately enlarged past the cylinder's own diameter (to `0.09`) for tunneling-resistance reasons unrelated to stacking — see the tunneling note under Throwing; re-verified at that larger size that all 40 pieces still reach `sleeping` within a few seconds undisturbed, so the box no longer needs to stay inscribed, just stay well short of the `0.5 m` gap between neighboring stacks.

**A rare corner-balance case still needed a script-level safety net (found and fixed once, worth knowing about):** after an extended play session with many varied hits, a struck kyykkä occasionally ends up balanced on a `BoxShape3D` corner/edge and spins in place indefinitely — diagnosed directly: reported velocity (linear + angular magnitude) held around 3-3.5 for 10+ seconds straight while its position barely changed at all, i.e. genuinely spinning on the spot, not tumbling anywhere; damping alone never arrested it. Rather than chase this specific unstable-equilibrium geometry through more material tuning, the fix is a small watchdog: if a body isn't asleep but also hasn't moved more than `STUCK_POSITION_THRESHOLD` (2 cm) in `STUCK_TIMEOUT_SECONDS` (2s), it forces `sleeping = true` and zeroes both velocities. Verified by reproducing the exact scenario (14 varied-gauge throws, then watching for 10s) — previously one piece spun forever, now all 40 settle to zero velocity. The karttu turned out to need the exact same safety net for a different reason (see below), so this watchdog now lives on a shared `scripts/settling_body.gd` (`class_name SettlingBody extends RigidBody3D`) base class instead of being duplicated; `Kyykka` and `Karttu` both `extends SettlingBody` and add nothing or their own behavior on top.

**Karttu needs continuous collision detection or it can tunnel through pieces (found and fixed once, worth knowing about):** at ~17 m/s the karttu moves roughly 0.28 m per physics step — several times a kyykkä's diameter — so without CCD it can pass straight through a piece between two discrete steps with zero collision response. Diagnosed directly with a deterministic point-blank test (no aim/flight involved): a moving karttu passed through a target with `continuous_cd` unset but woke/hit one immediately once it was set. This likely explains at least some of the earlier "sometimes connects, sometimes doesn't" throw variance noted in Phase 3 — though see the spin-lock note above for a *second*, separate way CCD could still be defeated even with `continuous_cd = true`.

**Ground friction shouldn't be lowered globally — it drags down everyone touching it, not just the karttu (found and fixed once, worth knowing about):** the ground's `StaticBody3D` used to carry a low-friction (`0.1`) `PhysicsMaterial` so a thrown karttu would slide through a target instead of stopping dead. Godot combines two contacting bodies' friction multiplicatively (there's no per-material `friction_combine_mode` — checked `PhysicsMaterial`'s property list directly, it doesn't exist), so that low ground friction applied to *every* body touching the ground, kyykkä included: giving `kyykka.tscn` its own high-friction material made no measurable difference (identical simulation results before/after — the ground's `0.1` still dominated the product). Worse, a struck kyykkä diagnosed with a plain 4 m/s slide never actually reached `sleeping` — it decelerated to a small residual speed (~0.07 m/s) and then rocked in place on a `BoxShape3D` corner forever, which is what "falls off the ground and moves around endlessly" turned out to mean (confirmed with the user: only happened to pieces after being hit, not at rest). Fixed by moving the low-friction behavior entirely onto `karttu.tscn`'s own material (removed from the ground) plus raising kyykkä's own damping (`linear_damp` 0.5→1.0, `angular_damp` 0.5→3.0 — the higher angular damping specifically kills the corner-rocking) — a struck piece now travels a believable ~0.7 m and reaches sleep within ~1s, verified directly with the same 4 m/s test. Later lowered back to `linear_damp` 0.5 / `angular_damp` 1.0 because flush hits barely moved the pieces: measured over 8 aimed flush throws, mean travel of struck kyykkä went from 1.10 m to 1.40 m with no change in settle time, and re-verified that stacks at rest still sleep with no drift and all 40 pieces settle after 14 varied throws — the `SettlingBody` watchdog (added after this fix) now backstops the corner-rocking case the high angular damping was originally for. Lowering friction too (0.6) added a little more travel but slowed settling, so friction stayed at 0.9.

**`linear_damp`/`angular_damp` act as continuous drag for a body's whole life, not just once it's resting — a single constant can't serve both flight and landing (found and fixed once, worth knowing about):** giving the karttu damping so a *landed* piece actually stops (see the watchdog note above — the karttu turned out to need it too, since it otherwise never naturally reached `sleeping`, only ever "settling" because `ThrowController` reset it after a timeout) also applies that same damping *during the throw itself*, acting like heavy air resistance. Diagnosed directly: at a damping value high enough to stop a landed karttu quickly (`3.0`), horizontal speed during flight decayed from ~17 m/s to ~3.7 m/s within 0.5s, covering only ~5m instead of the ~10m needed to reach the pesä. Fixed in `scripts/karttu.gd` by switching `linear_damp`/`angular_damp` between two exported pairs depending on phase — `flight_linear_damp`/`flight_angular_damp` (near zero) while `start_spin_lock()` is active, `landed_linear_damp`/`landed_angular_damp` (`2.0`/`3.0`) from `stop_spin_lock()` onward (called both by `ThrowController._reset_karttu()` and by the karttu itself on first contact) — rather than one constant trying to serve both.

**Godot's `continuous_cd` doesn't reliably catch a fast RigidBody hitting another (resting) RigidBody, only fast-vs-static (found and fixed once, worth knowing about — and a follow-up fix that was tried and reverted, see below):** even with `continuous_cd = true` and the spin lock correctly living in `_integrate_forces` (see above), throws that were geometrically confirmed to pass squarely through a kyykkä's collision volume — traced frame-by-frame, position and height both correct — still registered zero contact. Root cause, found by comparing a direct point-blank test (which *did* register a hit) against a full-arc throw (which didn't): at 60 physics ticks/second, the karttu's ~0.22–0.25 m of travel per step is several times larger than a kyykkä's collision depth (`0.0495 m`, an inscribed square — see the stacking-stability note above for why it's inscribed rather than the full `0.07 m` diameter), so the piece's whole thin collision volume fits *inside* a single step's motion — the position sampled at the end of one step is still short of it, and the very next step is already past it, with no discrete sample ever landing inside it. `continuous_cd` in Godot only reliably prevents a fast body tunneling through *static/kinematic* geometry (a thin wall) via a motion-clamping raycast; it does not extend the same guarantee to a fast body sweeping through another *dynamic* `RigidBody3D`, which is exactly this case (a resting-but-dynamic kyykkä).

Three fixes, in order. (1) Raising `physics/common/physics_ticks_per_second` to `240` did fix the headless miss, but was reverted after the user reported "I don't see a karttu moving at all now, it just resets" — which was blamed on the 4x solver cost *without evidence*. In hindsight that report was almost certainly the karttu-never-wakes-up bug (see the sleeping-flag note below: every throw after the first never moved, at any tick rate), not performance. (2) Enlarging the kyykkä's `BoxShape3D` from the inscribed `0.0495 m` square to `0.09 m` (still well short of the `0.5 m` gap between stacks; re-verified 40/40 pieces still reach `sleeping` within 4s undisturbed) — a better target, but a ~0.27 m step still usually skips a 0.09 m one: a throw aimed squarely at the row, passing through it at the right height, still moved zero pieces. (3) **What actually fixed it: hand-rolled CCD in `Karttu._stop_short_of_next_hit()`.** Every physics step the karttu `cast_motion`s its own collision shape along the motion it's about to make (excluding itself and whatever it's already touching, so resting on/sliding along the ground doesn't stall it); if that would pass into something, only that one step's velocity is scaled down to end touching it, and the full velocity is restored at the start of the next step so the solver resolves a real full-speed impact. At the default 60Hz, `tools/simulate_throws.gd` went from 25–31% contact to **16/16** throws aimed at a standing kyykkä actually hitting it. The padded box was kept.

**The spin lock's forced angular velocity shouldn't carry over into the real physics solver at the moment of release, or the landing tumbles chaotically instead of settling (found and fixed once, worth knowing about):** the locked spin (`scripts/karttu.gd`, see above) sets `state.angular_velocity` directly every step purely to drive the kinematic rotation — it isn't real accumulated momentum. Leaving that value in place at the instant `_integrate_forces` detects first contact and hands control back to the solver meant the solver received a large, physically-arbitrary spin as if it were genuine momentum, which combined with the contact impulse to send the karttu cartwheeling through multiple full rotations in the few frames right after touchdown (traced directly: rotation swinging between roughly -140° and +130° frame to frame, instead of settling) rather than sliding predictably. Fixed by explicitly zeroing `state.angular_velocity` in the same branch that calls `stop_spin_lock()` on release, letting the real contact impulse (not the leftover kinematic spin) determine any post-landing rotation.

**Only the very first throw of a session actually flew — every throw after that resolved instantly with the karttu never moving at all (found and fixed once, worth knowing about, and *the* reason for the "collisions are almost worse now" / "it's still not throwing anything" reports — the actual root cause, not the tunneling issues above):** reported directly by the user as "it immediately changes to other player's turn," and confirmed with real console output — `_await_settle()` returned after a single physics frame, with the karttu's `sleeping` flag reading `true` both before *and immediately after* `_karttu.freeze = false; _karttu.linear_velocity = launch_dir * throw_speed`. A sleeping `RigidBody3D` is skipped by the physics step entirely, so assigning it a velocity while it's still asleep has no effect — it just sits there, `_await_settle()` sees every watched body (including the un-moved karttu) already asleep on its first check, and the turn advances instantly. `_reset_karttu()` freezes the karttu between turns, which leaves it marked `sleeping = true`; unlike what's commonly assumed, merely setting `linear_velocity` does not reliably clear that flag on unfreeze. **Every headless test written earlier in this session missed this** because they only ever drove a single first throw from a fresh scene load, which happens to start non-sleeping by luck of initial spawn state — the bug only appears from the *second* throw onward. Diagnosed by adding temporary debug prints to the real `ThrowController._throw()`/`_await_settle()` path and having the user run the actual game (headless repro attempts — held swing, quick click, synthetic input events — all failed to reproduce it, since none of them threw twice in the same run). Fixed with one line: explicitly set `_karttu.sleeping = false` alongside `_karttu.freeze = false` at the start of `_throw()`, rather than relying on the velocity assignment to wake it. Re-verified headlessly by driving four throws in a row: all four now take the expected ~3.6s / ~220 physics frames to settle and show real motion, not just the first.

**Karttu mass and landed damping are tuned for sweeping through the pesä along the ground (tuned once, worth knowing about):** raising mass alone does *not* make the karttu slide further — damping and friction decelerate every body at the same rate regardless of mass (measured: 1 kg→2 kg at landed damping 3.0 left ground slide unchanged at ~4.4 m). What mass changes is collisions: a heavier karttu keeps more speed through each kyykkä and hits them harder. Measured over 14 throws per setting (half aimed at the row, half landing ~2 m short to slide in): mass `2.0` with `landed_linear_damp` `2.0` slides ~6.6 m instead of ~4.4 m, struck pieces travel ~1.63 m instead of ~1.23 m, and `tools/simulate_throws.gd`'s score rate went from 19% to 56% with contact still 16/16. Landed damping `1.5` cleared more still but slid the karttu off the end of the court, hitting the 5 s settle timeout on 13 of 14 throws — keep the post-landing slide short enough to stop around the pesä's back line.

**Aim model: point at where it should arrive, not along the throw (found and fixed once, worth knowing about — the reason for repeated "it doesn't reach the kyykkä" reports):** the karttu used to be launched straight along the camera's look direction. From the camera's default spot (1.6 m up, 1.2 m behind the thrower) the kyykkä row sits ~7.5° *below* horizontal — so the natural move, pointing the camera at the target, threw the karttu downward from 3 cm off the ground: reproduced headlessly, it touched down **0.74 m** out (row at 10.15 m). Only an unaimed +13° default, pointing the camera at the sky, reached — and every earlier headless test only ever threw at that untouched default, which is why repeated speed/elevation retuning (`14.8`/`15°`, then `16.0`/`13°`) "verified" fine while the user's real throws, logged at pitches like -0.8°, -7.8°, -10°, kept falling short. Now `_aim_distance()` casts the look ray to `aim_target_height` and `Ballistics.launch_elevation()` solves the arc at the fixed `throw_speed = 16.0`; verified headlessly that throws come down through aim height within ~0.1 m of the aimed point (10.19→10.18 m, 5.86→5.82 m, 14.38→14.28 m). `launch_elevation_degrees` (-7.5°) is now the *camera* pitch reset each turn, `min_elevation_degrees` -20° ≈ a 3 m throw (the old -10° floor couldn't aim short of ~8 m).

**Karttu damping must REPLACE, not COMBINE with, the project default (found and fixed once, worth knowing about):** every `RigidBody3D` defaults to `DAMP_MODE_COMBINE`, which adds `physics/3d/default_linear_damp` (0.1) on top of its own — so the karttu's "zero" flight damping still dragged every throw ~7% short of the drag-free arc. That's what the long-standing "simulated range diverges from the textbook formula" caveat actually was. `Karttu._ready()` sets `linear_damp_mode`/`angular_damp_mode` to `DAMP_MODE_REPLACE`, which is what lets `Ballistics` be exact.

**`tools/simulate_throws.gd` is a permanent (not throwaway) headless tool for exactly this kind of tuning** — run it directly (`godot --headless --path . --script tools/simulate_throws.gd -- [count]`) to spread swing-gauge timing across many throws at realistic distance and get contact-rate/score-rate/settle-time stats without needing a manual playtest for every physics tweak. Each throw points the camera (yaw and pitch, like a player lining up the crosshair) at the *outermost* kyykkä still standing, not dead center, re-picked every throw (aiming at one fixed spot kept throwing at empty ground once the first hit cleared it): the pesä is a full 5×5 m square, and a piece struck dead center — the point farthest from any boundary — has to travel the whole remaining ~4.85 m depth to register as a rules-engine score, which even a solid mechanical hit often can't manage; that's a property of the scoring rules (a large square is supposed to be hard to clear), not a physics bug, and it made every dead-center throw read as a "miss" even when tracing piece positions directly showed multi-metre real hits. The tool reports "contact" (did any watched piece actually move, a low bar that's the sensitive signal for a collision/tunneling regression specifically) and "scored" (did that movement cross a rules-engine zone boundary, the gameplay-relevant one) separately for this reason. None of this — aim sensitivity, swing timing feel, the cancel indicator, how it actually *feels* to throw — has been checked visually. I don't have a safe way to view this session's live display (see git history around the Phase 3 commits). Expect to retune further once someone actually plays it.

## Rules engine

`scripts/rules/` implements the game rules (README.md) as plain `RefCounted` GDScript classes with no `Node`/scene dependency, so they're directly testable and reusable once physics (Phase 3) and UI (Phase 5) need to drive them:

- `Team` — minimal, just a name for now.
- `Pesa` — one team's playing square: `in_square`/`on_line`/`removed` kyykkä counts and the `apply()` transition between them. Positions aren't modeled yet (no physics), so a piece's zone is just asserted directly by whatever calls `apply()` — currently the tests, eventually Phase 3's collision detection.
- `ThrowResult` — one throw's effect on a `Pesa`; this is the seam Phase 3 will produce instances of.
- `Attack` — one team's attempt to clear the opponent's `Pesa` within a karttu budget; owns `score()`, which is only meaningful once `is_finished()` (asserts otherwise).
- `Half` — both teams' simultaneous `Attack`s against each other's square. `next_attack(current)` is the turn-order rule `MatchController` drives from: alternates to the other side unless it's already finished, in which case the unfinished side continues alone. Turn order lives here (tested, no scene dependency) rather than in `MatchController`, since it's a game rule, not orchestration.
- `KyykkaMatch` — `HALVES_PER_MATCH` halves, `total_score()`, `winner()` (`null` on a tie).

`Attack.PENALTY_IN_SQUARE`/`PENALTY_ON_LINE` and `KyykkaMatch.DEFAULT_KYYKKA_PAIRS`/`DEFAULT_KARTTU_BUDGET` are the values that were least certain from the rule sources (see README.md) — they're named constants specifically so they're easy to correct against the official Suomen Kyykkäliitto rulebook without hunting through logic.

## Commands

Run via `make` (see `make help`); each target just wraps a `tools/*.sh` script or a direct Godot CLI call:

- `make run` — run the game (`tools/run.sh`, wraps `godot --path .`)
- `make edit` — open the project in the editor (`godot -e --path .`)
- `make check` — headless smoke test: loads the project and main scene, then quits. Useful to catch script/scene errors without a display: `godot --headless --path . --quit`
- `make export PRESET="<preset name>" OUT=builds/kyykka` — export a build (`tools/export.sh`). This requires export presets to exist first — none are checked in yet. Create them once via the editor (Project > Export...), which writes `export_presets.cfg`, and install matching export templates first (Editor > Manage Export Templates). `export_presets.cfg` is safe to commit once it exists.
- `make clean` — remove local build/import artifacts (`.godot/`, `builds/`)
- `make test` — run the [GUT](https://gut.readthedocs.io/) test suite (`tests/`) headlessly. GUT is vendored directly at `addons/gut` (copied from the `addons/gut` subfolder of the [Gut repo](https://github.com/bitwes/Gut) tag `v9.7.1`, not a submodule — that repo's top level is itself a demo Godot project, so only its inner `addons/gut` folder is the actual redistributable addon) and enabled as an editor plugin in `project.godot`. After first cloning, or after touching anything under `addons/`, run `godot --headless --path . --import` once so Godot registers GUT's `class_name`s before `make test` will work.
- There is no dedicated linter configured. [gdtoolkit](https://github.com/Scony/godot-gdscript-toolkit) (`gdformat`, `gdlint`) is the common external option if one is wanted later — it is not installed as part of this repo.

## Project structure

- `project.godot` — engine config; `run/main_scene` points at `scenes/main_menu.tscn` (the game boots into the menu, which then loads `court.tscn`); `[editor_plugins]` enables GUT.
- `scenes/` — `.tscn` scene files. `main_menu.tscn` is a tiny scene whose only job is to be the boot target for `scripts/ui/main_menu.gd`. `court.tscn` holds the camera, sun light, and world environment; the court geometry itself is generated at runtime by `court.gd` (see Court and equipment above). `kyykka.tscn`/`karttu.tscn` are the equipment props.
- `scripts/` — GDScript files. `court.gd` is attached to the `court.tscn` root and instantiates `match_controller.gd` plus the UI overlays (`scripts/ui/hud.gd`, `scripts/ui/pause_menu.gd`, `scripts/ui/results_screen.gd`); `match_controller.gd` in turn instantiates `pesa_view.gd`/`scripts/throwing/*` at runtime (none of these have a `.tscn` of their own — see Court and equipment / Match flow / UI / Throwing above). `kyykka.gd`/`karttu.gd` are attached directly to their respective `.tscn` equipment files and both `extends` the shared `settling_body.gd` (`class_name SettlingBody`) for the "force-settle if stuck" watchdog — see the corner-balance note under Throwing. `scripts/rules/` is the rules engine (see Rules engine above). `scripts/ui/` is the Phase 5 UI (see UI above).
- `tests/rules/`, `tests/scenes/`, `tests/throwing/` — GUT tests, mirroring the `scripts/` layout: one `test_*.gd` file per class.
- `addons/gut/` — vendored GUT addon (see Commands above); third-party code, not maintained here.
- `assets/` — art/audio/etc. (currently empty).
- `Makefile` — common command entry points (see Commands above).
- `tools/` — repo-local shell scripts the Makefile wraps (`run.sh`, `export.sh`), not Godot engine code.
- `.godot/` is the engine's local import/cache directory, regenerated automatically and gitignored — never edit or commit it.
